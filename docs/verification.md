## Known limits

- The encryption has had no outside review.
- No forward secrecy. A leaked device key exposes recorded messages to that device.
- The root key sits on the same device as the device key, locked with a passphrase. Someone who steals the laptop and the passphrase is you until contacts remove you by hand. Revocation is not built.
- The passphrase protects against other programs running as you, not against a compromised machine. A keylogger or a replaced `cpart` binary can capture it.
- Approvals cannot be revoked. That is by design, and the approval screen says so.
- With a locked root key the device credential (90 days) is renewed by hand with `cpart renew`.
- One device per person.
- Nobody runs a relay for you. You run one, or use someone else's.
- Everything has run on Linux. Nothing has run on macOS or Windows.
- `cpart relay --tunnel` gets a new address each start. `cpart relay move` takes contacts along, but only while the old address still answers; if a tunnel dies first, contacts on it must be told the new address another way. A contact on a version older than 0.3 cannot follow a move.
- The background daemon is a plain process, a systemd user unit, or a launchd agent. The launchd agent, for the daemon or the relay, has not been run on a Mac. `scripts/mac-check.sh` does it.
- `cpart setup` changes your Claude Code and Codex settings by calling their own `mcp add`. It says so as it does it; `--no-agents` skips it.
- A worker's patch is reviewed by a person and never run locally. The checker limits which files it can touch; it cannot tell whether ordinary source code in an allowed file is safe. Read the patch.
- Evidence from the other side is their claim. Your machine checks the digests they name against the signed contract, not what their repository holds. A sender who lies can name the right digests. Their CI status on a repository you can see is the stronger check, and nothing yet ties evidence to it.
- The relay sees which device writes to which, when, and how much, and stores sender and recipient with each queued message.
- A stranger who sends 1000 junk messages pushes older entries out of the refused-messages log.
- A coding session that reads a peer's reply through the MCP tools is reading untrusted text, like reading a web page. The reply is wrapped and labelled. In the latest red team run no session sent a secret on, but an earlier run leaked a live key in two trials ([redteam.md](redteam.md#results)), and nothing in code stops a session with shell access from being talked into something. Grants, which would limit such a session, are not built ([design.md](design.md#not-built)); only its own permission prompts limit it. Use the MCP tools in sessions where you approve commands yourself.
- With a subscription login the front desk model runs through the `claude` CLI, which adds the account email, OS version and date to the model's context. Replies containing those exact values are dropped, but an encoded form would get through if the model were talked into it. With `ANTHROPIC_API_KEY` set the model sees only what we send; that path is tested against a fake server, not the real API. `scripts/frontdesk-api-check.sh` runs it for real once you have a key.
- The front desk and the worker run on Claude only. Codex cannot be started with no tools and does not report its tool calls ([design.md](design.md#decisions-and-why)). The Anthropic API-key adapter has only been run against a local stand-in server. There is no OpenAI API adapter.
- A lost message is recovered only while its author is reachable and still has it. Each event is sent again at most five times. If the pairing acceptance itself is lost, nothing asks for it again.
- A receipt is the other daemon's claim. A contact can withhold receipts, so "at relay" in `cpart log` does not prove a message was not applied.
- A session learns of a reply through hooks: on its next step, when it tries to stop, or, in interactive Claude Code in a terminal, by being woken when idle. Codex cannot be woken when idle, and runs the hooks only after you trust them. Each notice can start a model turn; the other side can cause at most 20 an hour.
- The outbound guard catches what it can recognise or knows. A secret it does not know and has no known shape (a key only in git history, a password in a database), an encoding not on its list, or an agent with a shell that sends it some other way (curl) gets through. It is a seatbelt, not a sandbox. See [guard.md](guard.md).
- Short-code pairing trusts the relay not to end pairings: it can make one fail, never complete one. The relay keeps nameplates in memory, so a relay restart ends live codes.
- A question put only in the thread goal is answered by the front desk after 20 s only if the goal has a question mark. A goal without one, followed by no message, gets no answer.
- With the front desk off (the default), nothing answers on its own. The owner is told a contact is waiting (status and the next session), but the asker's agent is not told that nobody is answering.
- A key piece of fewer than 8 random characters after its fixed prefix gets through the guard (for example `sr_live_` plus 4, or the first 12 and last 4 characters of a key).
- A contact whose device credential has expired cannot be written to until they send something.
